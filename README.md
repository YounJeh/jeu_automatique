# Mastra Prompt-to-Game

**Turn a natural-language sentence into a playable 2D browser game — validated, simulated, and provably playable before a single frame is rendered.**

> "Create a game where I dodge falling meteors for 30 seconds."
> → a structured `GameDefinition`, schema-checked, semantically validated, playability-scored, headlessly simulated, and running in `<canvas>` in seconds — no LLM-generated code ever executes.

This repository is a working case study in **constraining an LLM inside a deterministic engine** rather than letting it write arbitrary code. The model's only output is structured data; every game mechanic, rule, and win/loss condition is a closed, typed, tested primitive owned by the codebase.

---

## Why this repo is worth reading

Most "AI generates a game" demos let a model emit code or free-form JSON and hope for the best. This project takes the opposite bet, and the codebase is built to prove it out end to end:

- **The LLM never writes code.** It selects mechanics and fills in a strictly-typed `GameDefinition` (Zod, `.strict()`, closed enums for entity kinds, rule events, and rule actions). No `eval`, no `new Function`, no dynamic imports of model output.
- **Three independent validation layers**, not one: schema (shape) → semantic (internal coherence — is the goal reachable, are references valid) → playability (deterministic heuristics that catch a _technically valid but unplayable_ config, e.g. obstacle density that makes dodging impossible).
- **Playability is computed, not judged by the model.** Rules like "can the player structurally never escape a pursuer moving faster than them" are arithmetic on the definition, not a prompt asking an LLM if a game "seems fun."
- **A generic, declarative game runtime** (`GenericRuntime`) executes any valid `GameDefinition` — movement, spawning, collision, rules, goals, rendering — with an injectable RNG for deterministic replay, headless simulation, and testing.
- **Generation quality is a measured eval suite, not a vibe check.** A versioned dataset of prompts (`tests/evals/game-generation-cases.json`) asserts structural properties (mechanics present, goal reachable, runtime loads, N headless simulation runs with zero runtime errors) for every case — including adversarial and impossible prompts, which are expected to safely fall back to a preset rather than fail.
- **408 tests across 63 files**, a phased, documented delivery process (`CLAUDE.md`, 11 phases, each with explicit scope and _forbidden_ work), and a full quality gate (`pnpm check` = typecheck + lint + unit tests + build, plus a separate Playwright E2E suite) enforced before any phase is considered done.
- **Backward-compatible evolution, not rewrites.** Three legacy per-template engines (`dodge`, `collect`, `shooter`) still run in production behind a feature flag while the generic `GameDefinition` runtime is proven out incrementally — each new mechanic (e.g. a "seek" movement pattern for a pursuing enemy) is added with its own schema change, runtime behavior, dedicated playability rule, docs, and tests before it ships.

If you're evaluating this as a signal of engineering judgment: the interesting part isn't the canvas game, it's the discipline around **what the LLM is and isn't trusted to decide**, and the validation/simulation/eval machinery built to make that trust boundary enforceable and measurable.

## Architecture

```
User prompt (natural language)
        │
        ▼
  Mastra agent  ──────────────►  selects mechanics from a closed registry
        │                        (move, avoid, collect, shoot, health, score, timer)
        ▼
  GameDefinition (structured output, Zod-validated)
        │
        ▼
  Schema validation      — shape, types, closed enums, strict objects
        │
        ▼
  Semantic validation    — is this internally coherent? (goal reachable,
        │                   entity references valid, no impossible state)
        ▼
  Playability validation — is this a *good* game? deterministic heuristics,
        │                   never an LLM judgment call
        ▼
  [invalid] ──► 1 bounded structured repair attempt ──► [still invalid] ──► fallback preset
        │
        ▼
  GenericRuntime          — deterministic engine: movement, spawn, collision,
        │                    rules, goals, timers, injectable RNG
        ▼
  Headless simulation (eval/CI)   ◄────────┐   Canvas rendering (browser)
        │                                   │
        ▼                                   ▼
  SimulationMetrics                   Playable game
  (win rate, avg duration,
   runtime errors)
```

**Data over code, everywhere:**

```
game = GameDefinition (data)  +  GenericRuntime (deterministic engine)
```

never

```
game = new code generated by the LLM
```

### Layered validation, concretely

```ts
type PlayabilityIssue = {
  severity: "warning" | "error";
  code: string;
  message: string;
};
```

Example rule (`game-definition-playability-rules.ts`): a pursuing enemy (`movementPattern: "seek"`) moving at or above the player's speed is flagged — once spotted, the player can _never_ structurally lose it. That's arithmetic on `entity.speed` vs `player.speed`, computed once per generation, not an opinion.

### GameDefinition v1 (excerpt)

```ts
type GameDefinition = {
  version: "1";
  metadata: GameMetadata;
  world: WorldDefinition;
  player: PlayerDefinition;
  entities: EntityDefinition[];
  mechanics: GameMechanic[]; // closed set, validated against a dependency graph
  rules: GameRule[]; // { when: RuleEvent; then: RuleAction[] } — closed vocab
  goals: GoalDefinition[]; // survive | score | destroy
  presentation: PresentationDefinition;
};
```

Rule events and actions are closed vocabularies (`player-collides-enemy`, `timer-expired`, `damage-player`, `spawn-entity`, …) — never free-form expressions, never anything resembling executable logic.

### Mechanic registry with dependency validation

```ts
export const mechanicRegistry: Record<GameMechanic, MechanicDefinition> = {
  move: { id: "move", dependencies: [] },
  avoid: { id: "avoid", dependencies: ["move"] },
  collect: { id: "collect", dependencies: ["move"] },
  shoot: { id: "shoot", dependencies: ["move"] },
  health: { id: "health", dependencies: [] },
  score: { id: "score", dependencies: [] },
  timer: { id: "timer", dependencies: [] },
};
```

Templates are just named compositions: `dodge = move + avoid + timer`, `collect = move + collect + score + timer`, `shooter = move + shoot + avoid + health + score`, `survival = move + avoid + health + timer`. Adding a new game family starts by asking _which primitive is actually missing_ — not by building a bespoke engine.

## What's actually implemented

| Layer               | Status                                                                                                                                                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Game families       | `dodge`, `collect`, `shooter` (legacy per-template engines, in production) + `survival` (first `GameDefinition`-only family, generic runtime)                                                                              |
| Validation          | Schema (Zod, strict) → Semantic → Playability, fully separated, independently tested per template and generically                                                                                                          |
| Runtime             | Legacy per-template engines **and** a generic `GameDefinition` runtime (`GenericRuntime`), gated by `GENERIC_RUNTIME_ENABLED`, migrated incrementally with the legacy path kept as fallback                                |
| Generation pipeline | Mastra workflow: receive request → infer `GameDefinition` → schema/semantic/playability validation → one bounded structured repair → fallback preset → save → catalog                                                      |
| Simulation          | Headless, seeded, N-run batches producing `SimulationMetrics` (win rate, avg duration, avg score, runtime errors) — used both in CI eval assertions and available for tuning difficulty                                    |
| Evaluation          | Versioned dataset (`tests/evals/game-generation-cases.json`) asserting structural properties per prompt — including ambiguous and impossible prompts, which must safely resolve to a fallback preset, never a hard failure |
| Observability       | Structured per-generation log record: mechanics selected, validation result, repair attempted, fallback used, runtime load result — no prompts, no chain-of-thought, no secrets                                            |
| Assets              | Closed asset catalog (`AssetCatalogItem`) referenced by id — the LLM can never write an arbitrary URL, path, or inline SVG/HTML into the runtime; sprite load failure always falls back to a plain shape                   |
| Frontend            | Lightweight, no-framework TS + Canvas — chat panel, live generation status, game catalog sidebar, single server (Mastra) serving both the API and the static app                                                           |
| Security posture    | No `eval`/`new Function`, no LLM-authored paths/URLs/HTML, no client-side API keys, every external input (prompt, LLM output, saved games) treated as untrusted and validated at the boundary                              |

## Engineering discipline

- **Phased delivery, enforced.** `CLAUDE.md` defines 11 phases (MVP → hardening → new template → shared systems → composable mechanics → `GameDefinition` v1 → generic runtime → presets → simulation/eval → controlled assets → new game families → experimental generation), each with an explicit goal, scope, exit criteria, and a list of things _forbidden_ until earlier criteria are met. The current phase is tracked in [`docs/current-phase.md`](docs/current-phase.md) as a single source of truth, not a changelog.
- **Every mechanic is documented like a contract.** [`docs/mechanics/`](docs/mechanics) — purpose, dependencies, exact runtime behavior with file/line references, events emitted, actions supported, validation rules, and the tests that cover each claim. See [`avoid.md`](docs/mechanics/avoid.md) for an example of a mechanic with two movement patterns (`fall`, `seek`), each with its own dedicated playability formula.
- **Git history reads like a spec, not a diary** — one atomic, reviewable commit per capability (schema change → runtime behavior → validation rule → catalog wiring → e2e coverage → docs), never a rewrite.
- **TypeScript strict**, no `any`/`as unknown as`/`@ts-ignore` without justification, exhaustiveness checked at compile time via `assertNever`.
- **Deterministic by construction.** `RandomSource = () => number` is injected everywhere entities spawn or move randomly — the same definition + seed reproduces the same run, which is what makes headless simulation and CI eval assertions meaningful instead of flaky.

## Tech stack

- **TypeScript** (strict) — no bundler for the frontend; a small vendoring script (`scripts/vendor-zod.mjs`) ships Zod to the browser directly.
- **Mastra** — the single agentic orchestration framework, used workflow-first: deterministic steps for anything predictable, one agent (`gameDesignerAgent`) for the one step that genuinely needs a model.
- **Zod** — schema validation for every LLM-facing and user-facing boundary.
- **Vitest** — unit + integration + eval-dataset tests.
- **Playwright** — E2E: catalog play, generation chat flow, generic-runtime play, shooter play.
- **HTML5 Canvas** — rendering, no game framework dependency.

## Roadmap

The project follows a strict "prove the need before building the abstraction" rule (`CLAUDE.md` §41, §17): no ECS, no free-form code generation, no ORM, no framework churn without a concrete pain point from three-plus real templates. Active direction:

```
templates (done)
  → shared systems (done)
    → composable mechanics (done)
      → GameDefinition v1 (done)
        → generic runtime (in progress, dodge/collect/shooter legacy fallback kept)
          → templates as presets (in progress)
            → simulation & eval (in progress, dataset-driven)
              → controlled assets (in progress, closed catalog)
                → new game families (in progress — survival is the first)
                  → sandboxed experimental generation (not started, deliberately last)
```

---

## What this project is not (on purpose)

No multiplayer, no accounts, no database (JSON + localStorage is enough for now), no 3D, no ECS framework, no free-form code generation reaching the runtime, no multi-agent orchestration for its own sake. Every one of these is explicitly deferred in `CLAUDE.md` until a real product need demands it — scope discipline is treated as a feature, not a limitation.
